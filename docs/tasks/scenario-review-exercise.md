# Scenario reuse: bounded review exercise

## Purpose and authorization

Prepare one small public Demo exercise to investigate whether one-level inclusion
and named results help a person review changes without overlooking obligations.
Preparation is authorized; no submission is authorized. Human review is a later
gate. Neither passing tests nor fewer lines establishes a human cost saving.

Use only public Demo code, the shipped Scenario contract, and the synthetic
requirements below. Do not access private products or workroom material. Do not
change core, adapters, YAML syntax, CI, existing examples, or historical evidence.
Do not add an editor, review service, mutation engine, or approval infrastructure.

## Fixed exercise requirements

This is a hypothetical review exercise, not a newly approved product requirement.
The participant may challenge these requirements before reviewing; doing so is
not an incorrect answer. A changed requirement starts a new exercise baseline.

1. Create one item named `review-draft`, sending rows `[1, 2, 3]`. Check a successful
   response, returned ID and requested name, and the existing Demo `item.create`
   span with `row_count == 3`.
2. Update that same returned ID to `review-final`; check success, the same response
   ID, and the existing `item.update` span.
3. Read the collection; check success and exactly one member matching that ID and
   `review-final`. This is not an assertion that the whole collection has one item.

The Demo's span is system-reported evidence, not an independent database audit.
There are no UI or contract-projection claims in this exercise. The projection
under test is backend, with the same evidence and checks in both representations.

## Paired source artifacts

Under `docs/review-exercise/`, store a baseline and three independent change cases.
Each directory has `included.yaml`, `included.includes.json`, `child.yaml`, and
`flat.yaml`. The child creates; the parent updates and reads using an explicit
`record_id` result. Keep one level and the same actor. The flat form is authored
independently, not generated by the include expander. Both forms retain identical
action inputs and assertions, modulo step names and source metadata.

The three changes are fixed; they are not cumulative:

| Case | Only intended change from baseline |
| --- | --- |
| `case-01` | Rename the child's internal create step and its result source; retain public result name. Update the pin. Make the corresponding local rename in the flat form. |
| `case-02` | Supply the final name instead of the draft name when creating. The child checks the supplied name, so the corresponding flat request and name assertion both change. |
| `case-03` | Remove only the creation `row_count == 3` assertion; retain the span-exists assertion and all other checks. Update the pin. |

Use neutral case numbers, not verdicts, in participant material. All versions
must validate and pass against the unchanged real Demo on their own clean test
server. This is deliberate: declaration validity and successful normal execution
are not permission to change the fixed requirements.

Store the answer key separately, marked for use after first review. It identifies
each intended decision, affected requirement, actual source differences, and the
limits of the evidence. Do not treat it as a hidden or tamper-proof oracle.

## Technical checks before human review

- Every source YAML loads; each sidecar pins the exact current child bytes.
- Materialize all three actions with fixed, distinct response IDs and compare
  included/flat concrete requests and checks. Explicitly map local step names;
  do not produce the flat source by expansion or omit checks from comparison.
- Compare baseline/case source differences against the changes above. In case-01
  the included parent is byte-identical and the child pin changes. A stale pin
  must fail loading. This does not mean the new child is automatically approved.
- Execute all eight parent/flat declarations (baseline plus three cases) using
  existing real Demo adapters and fresh servers; require PASSED/no degradation.
- Add a bounded synthetic evidence control: in a wrapper around the real Demo
  StateProbe, change only observed creation `row_count` from 3 to 2. Baseline and
  case-01/case-02 must detect it; case-03 must miss it, in both representations.
  Assert the unmodified observed value was 3 before replacement. This is an
  injected observation fault, not proof the product stored the wrong row count,
  not an independent evidence source, and not a general mutation score.
- Verify the wrong-wiring case actually sends `review-final` on creation; do not
  manufacture a verdict by replacing core checks or reading the answer key.
- Review excerpts/diffs must exactly match the YAML files. Provide full sources,
  unchanged baseline, child, and pins for inspection. A summary is not a second
  authoritative Scenario.
- Independent audit checks paired fidelity, fault-control behavior, answer-key
  reasoning, public sources, and the absence of invented human measurements.

## Human review protocol and stopping point

The first packet shows case-02 included, case-01 flat, then case-03 included. For
each, the participant records approve / reject / insufficient information, a
short reason, optional active minutes, files consulted, and clarification needs.
Include pin changes are visible, and child review effort is not discounted.
Reading setup/requirements counts separately from per-case review time.

After the first response, offer the opposite form of each same case. Keep the
first answers unchanged. Compare what was clearer, what was missed, and any
re-review/pin overhead. The second pass is exposed to learning; mixed first-pass
forms do not counterbalance that bias. This one-person, three-change exercise is
exploratory, not a causal or population estimate. Missing times remain unknown;
tool runtime, chat latency, AI reading speed and YAML length are not human time.
The participant may stop or skip the second pass; report incomplete evidence.

Do not silently publish personal review measurements. Keep the first responses
in the conversation unless the participant explicitly authorizes a scoped public
summary. Preparation can be accepted separately while human value is UNMEASURED.

Continue this direction only if review feedback identifies a concrete benefit
or a bounded fixable friction. Mixed/no improvement, extra pin burden, or missed
obligations is grounds to adjust or stop, not to authorize deeper nesting.
