# Scenario include: frozen backend fault controls

This acceptance asset is frozen before implementation against public baseline
`9bebfa7559bfc22e7121bc31b1945e803676a1f8`. It is synthetic, product-neutral,
in-memory backend evidence, not a product-quality or review-cost measurement.

The independently authored flat and included declarations, observed service
responses, and three fixed injections are in `tests/include_fault_controls.py`.
Neither form is generated by the loader/expander being tested. Each fault also
runs a fresh, non-injected passing neighbor with exactly the same declarations.

| Fault | Injected observation | Exact detecting check | Reachability and stop evidence |
| --- | --- | --- | --- |
| `accepted_rejection` | An empty-name POST normally returns HTTP 422 / `ok=false`; injection returns HTTP 201 / `ok=true`. | `reject`: `failure` | POST was sent; injection reached once; following GET is BLOCKED. |
| `changed_collection_target` | After a successful create, GET collection returns an unrelated first member and the target second member, but changes only the target name. | `list`: `collection_matching_count`, matching created response ID and declared name, count 1 | Create and list were sent; injection reached once; target observed with changed name; following read is BLOCKED. |
| `wrong_object_read` | Create returns `record-1`; a GET whose path uses that actual response ID returns `record-2` with the otherwise correct name. | `read`: `field_equals`, response ID equals create response ID | GET actually targets `records/record-1`; wrong-object response observed; injection reached once; following list is BLOCKED. |

The included form uses one same-actor child for create/rejection and qualified
response references. The remaining assertions, inputs, transport, normalization,
and response evidence are identical to the flat control. Source annotations and
the `setup/` step prefix are the only comparison exclusions. Fresh trace IDs and
timing are not part of these synthetic controls' compared output.

## Commands and outcome rules

Run the frozen harness with the target public checkout on `PYTHONPATH`, using a
Python environment with the project's locked dependencies. Run from outside the
source checkout if necessary; confirm `refracto.__file__` names the intended target.
`HARNESS` denotes the absolute path of this accepted public test script, and
`TARGET` denotes the isolated verification checkout; neither value is evidence.

```sh
PYTHONPATH="$TARGET" python "$HARNESS" --flat-only
PYTHONPATH="$TARGET" python "$HARNESS"
```

Baseline: first command, three valid executed faults detected, three passing
neighbors, exit 0. Baseline include rejection is a red-feature check, not a fault
detection. Candidate: both commands; flat and include each detect the same three
faults with passing neighbors, exit 0, and equivalent normalized observations.

Detection requires the exact intended failed assertion, an injection reached
exactly once, and no ERROR. Import/setup/declaration errors are `invalid_control`,
never detections. A reached valid fault without the intended assertion failure is
`missed`. Reports must retain exclusions; zero valid executions means `N/A`.
All three faults must be valid and executed in each accepted comparison form.
The relevant denominator is three per form, not the number of test functions or
the number of projections. No frontend/e2e/contract result is inferred here.

Actual baseline/candidate runs, commands, exit codes and immutable asset hashes
are appended in the final delivery record after execution. Do not change the
fault definitions to improve a result.
